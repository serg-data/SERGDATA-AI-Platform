# Отчёт проверки — Agent Tool-call / explicit registered project read

Дата: 07.11.2026
База для патча: `SERGDATA-Workbench-Next(20261106-202103).zip` от 06.11.2026; изменения оформлены как overlay только для перечисленных файлов.

## Диагноз по присланным журналам

В LM Studio в 00:22:13 модель вернула сообщение с двумя текстовыми блоками `<tool_call>` и `tool_calls: []`, `finish_reason: "stop"`. Это нормальное завершение генерации LM Studio, но не выполнение инструментов: вызовы пришли в `message.content`, а не в нативном массиве OpenAI `tool_calls`.

В журнале модель просила:

- `search_knowledge(query=..., limit=10)`;
- `read_uploaded_file(file_id=5)`.

В спецификации Workbench для `read_uploaded_file` обязательный параметр называется `attachment_id`, а не `file_id`.

В исходном `workbench/tool_call_adapter.py`, функция `parse_text_tool_calls()`, все блоки находились внутри одного `try`. Исключение на втором блоке возвращало пустой список вызовов и отбрасывало уже разобранный первый блок. В `workbench/agent.py`, `Agent.chat()`, обнаруженная ошибка адаптера вела к повторному запросу модели без выполнения любого из вызовов. Повторение некорректного формата могло исчерпать лимит раундов.

Отдельно журнал показывает, что модель пыталась читать абсолютный путь `F:\SERGDATA-Workbench-Next` через обычный `read_project_file`, хотя активный корень был `F:\AI-Projects\Lab`. Это правильно блокировалось защитой `ProjectTools.safe()`. Наличие пути в тексте вызова само по себе не должно выключать sandbox.

## Изменения и затронутые функции

- `workbench/tool_call_adapter.py` — `_normalize_argument_aliases()`, `parse_text_tool_calls()`, новая `strip_text_tool_call_markup()`. Валидные блоки сохраняются, ошибки агрегируются отдельно по номерам блоков; добавлен alias `file_id` → `attachment_id` только для `read_uploaded_file`.
- `workbench/agent.py` — `Agent.specs()`, новая ограниченная ветка в `Agent.tool()`, `Agent.chat()` и `_resume_saved_tool_context()`. Корректные вызовы выполняются даже при наличии отклонённого соседнего вызова; raw transport markup удаляется из текстовой части истории.
- `workbench/agent.py` — `_explicit_external_project_roots()` вычисляет временную область доступа только из точного корневого пути, буквально присутствующего в текущем пользовательском сообщении.
- Новые внешние инструменты только читают/перечисляют файлы внутри другого зарегистрированного корня. Активный `PROJECT_ROOT` не меняется.
- `tests/test_tool_call_adapter.py` — добавлены точные тесты логированного двухблочного ответа, alias, частично повреждённого пакета, повторной попытки и защиты от показа сырых `<tool_call>`.
- `tests/test_explicit_registered_project_access.py` — добавлены тесты точного совпадения корня, отказа без разрешения, чтения, списка, path traversal и отсутствия write/execute capability.

## Проверки

- `python -m pytest -q` — **236 passed**.
- `python -m compileall -q workbench tests` — OK.
- Точный сценарий из журнала LM Studio воспроизведён в unit/integration-style тесте адаптера и Agent: оба вызова приняты, `file_id=5` нормализован в `attachment_id=5`, следующий ответ модели возвращается как финальный.
- Проверен частично неправильный пакет: корректный вызов выполняется, неверный не запускается, модель получает указание повторить только отклонённый вызов.
- Проверены ограничения внешнего доступа: требуется точное указание корня в текущем запросе и регистрация этого корня в Workbench; дочерний путь не выдаёт доступ ко всему проекту; `../` блокируется.
