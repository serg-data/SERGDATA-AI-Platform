# Аудит автономного цикла и совместимости Tool Calling

Дата: 05.11.2026  
База: `SERGDATA-Workbench-Next(20261105-190259).zip`  
Работа выполнена в отдельной копии архива. Исходная папка пользователя и GitHub не затрагивались.

## Подтверждённые причины остановки

1. `Agent.chat()` и `_resume_saved_tool_context()` ориентировались только на `message.tool_calls` из OpenAI-compatible API.
2. Если модель помещала вызов в `message.content` в виде `<tool_call><function=...><parameter=...>...`, `message.tool_calls` оставался пустым. Агент воспринимал такой ответ как обычный финальный текст и завершал ход. Это соответствует журналу от 05.11.2026 23:20:48.
3. Формат вызова из журнала не совпадал со схемой `sandbox_run_check`: модель использовала `mode` и `args`, а схема принимала `command` и `path`; кроме того, Sandbox Manager не принимал список аргументов pytest. Поэтому даже простое включение текстового парсинга без согласования контракта не решило бы конкретный случай.
4. Повторный вызов с теми же аргументами глобально блокировался и приводил к `stop_reason`, хотя первый результат уже был доступен в истории. Агенту следовало повторно использовать сохранённый результат, а не останавливать всю задачу.

## Изменения в отдельной копии

- Добавлен `workbench/tool_call_adapter.py`: строгий адаптер для двух форматов текстовых вызовов (`<function>/<parameter>` и JSON внутри `<tool_call>`). Принимаются только зарегистрированные инструменты, параметры сверяются со схемой; неизвестные инструменты/параметры и незавершённые блоки отклоняются. Нативные `message.tool_calls` имеют приоритет.
- Основной цикл `Agent.chat()` и цикл возобновления после пользовательского ввода/подтверждения используют общий адаптер. Некорректный формат возвращается модели как ошибка формата с ограниченным повтором в пределах существующего лимита раундов; вызов не исполняется.
- Повторный идентичный вызов в рамках одного запроса больше не останавливает весь цикл: если результат предыдущего вызова есть, он подставляется повторно без повторного исполнения. Если успешного результата нет, повтор блокируется, но агенту даётся возможность выбрать другой шаг.
- Схема `sandbox_run_check` согласована с фактическим вызовом из журнала: поддерживаются `command`, совместимый алиас `mode` в текстовом адаптере и ограниченный список `args` для pytest.
- Аргументы pytest запускаются без shell, ограничены безопасными флагами и путями внутри Sandbox. Произвольные параметры pytest не принимаются.
- В UI добавлена подпись статуса повторно использованного результата.

## Проверки

- `python -m compileall -q workbench tests` — успешно.
- Целевые тесты адаптера, Sandbox, контекстов и возобновления — 38 passed до добавления интеграционного сценария; новые тесты также прошли.
- Полный `pytest`: в последних прогонах 191 passed / 1 failed из-за тайминга `test_subprocess_completion_callback_runs_after_output_capture` (ожидание завершения фонового subprocess 2 секунды). Этот тест отдельно проходит; полный набор без `tests/test_process_callable.py` — 188 passed. Это нестабильность уже существующего теста ProcessRegistry, не связанная с изменениями Tool Calling.
- Ruff недоступен в окружении (`No module named ruff`); lint-проверка не выполнена.
- Реальный запуск через LM Studio/Neohorse на Windows в этой среде невозможен. Исправление проверено unit- и integration-тестом с имитацией OpenAI-compatible ответов; реальную совместимость с установленным chat template ещё необходимо подтвердить на пользовательском ПК.

## Ограничения

- Sandbox остаётся файловой рабочей областью, а не OS-level sandbox. Запуск pytest исполняет Python-код на хосте с правами процесса Workbench.
- Этот патч не меняет механизм Windows/SSH подтверждений, не запускает SSH и не выполняет перенос в основной проект.
- До проверки на реальном LM Studio релиз нельзя считать окончательно подтверждённым.
