# Аудит подтверждения и продолжения выполнения — 06.11.2026

## Область проверки

Проверены обработчик `POST /api/execution/{eid}/approve`, атомарные переходы в `workbench/db.py`, процессный реестр `workbench/processes.py`, callback завершения, резервный путь `GET /api/processes/{jid}`, продолжение исходного tool call в `workbench/agent.py` и координация ветки в `workbench/execution_resume.py`.

## Подтверждённый дефект и исправление

До исправления отказ `claim_execution_approval()` выбрасывал `HTTPException(409)` внутри `try`, но ниже находился только общий `except Exception`. В результате конфликтный HTTP-ответ мог попасть в обработчик ошибки запуска: запись пытались перевести в `failed`, после чего запускалось продолжение агента, хотя первая команда могла ещё выполняться.

Исправление: перед общим `except Exception` добавлен отдельный `except HTTPException: raise`. HTTP-ответы управления потоком не меняют состояние выполнения и не запускают resume. Общая обработка реальных ошибок запуска сохранена.

## Проверенная цепочка результата

1. Подтверждение использует атомарный SQL claim: меняет `pending` на `running` только при совпадении исходного статуса.
2. Завершение процесса записывает результат только при статусе `running` через `finish_execution_once()`.
3. Callback процесса и резервный путь статуса используют этот же атомарный метод; только победившая сторона получает `changed=True`.
4. Продолжение модели защищено отдельным атомарным `claim_execution_resume()` (`waiting` → `running`).
5. `resume_execution()` восстанавливает сохранённый контекст, находит исходный `tool_call_id`, заменяет placeholder фактическим результатом и отправляет продолжение модели.
6. Если модель в ходе продолжения запрашивает ещё одну команду с подтверждением, контекст нового tool call сохраняется отдельно, а дальнейшее выполнение останавливается до подтверждения.
7. При перезапуске незавершённая команда не запускается повторно: состояние помечается неопределённым, пользователь получает предупреждение. Прерванное продолжение также не воспроизводится автоматически.

## Стабилизация теста

В `tests/test_process_callable.py` увеличено ожидание завершения фонового процесса с 2 до 5 секунд. При нагрузке среды 2 секунды иногда не хватало на запуск дочернего Python-процесса; это был таймаут теста, а не доказанный дефект `ProcessRegistry`. Производственный код процесса не менялся.
