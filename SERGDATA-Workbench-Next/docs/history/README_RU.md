# SERGDATA Workbench — локальная среда для LM Studio

Веб-интерфейс для проектов, задач, веток диалогов, истории, статистики токенов, работы с файлами и интеграции с существующим SERGDATA Knowledge MCP.

## Возможности этой сборки

- Локальный веб-интерфейс: переключение нескольких проектов, задачи и ветки слева/сверху, чат по центру, статистика, память и Git справа.
- LM Studio через OpenAI-compatible API.
- Сохранение истории в SQLite.
- Ветки диалога: новая ветка наследует историю до точки ответвления; дальнейшие сообщения независимы.
- Создание проектов из существующих папок, переключение проектов, создание задач в выбранном проекте, переименование/удаление задач и веток.
- Статистика фактических prompt/completion tokens из каждого ответа LM Studio; отдельно сохраняются вызовы инструментального цикла и внутреннее сжатие памяти.
- Предварительный подсчёт через токенизатор загруженной модели LM Studio и её prompt template, если установлен SDK `lmstudio`. Токены схем инструментов считаются отдельно как оценка, поскольку OpenAI-compatible API не предоставляет отдельный HTTP endpoint для точного preflight-подсчёта готового запроса.
- Автоматическое сжатие старой истории в постоянную память ветки: сохраняются факты, пути, решения, проверки, ограничения и следующий шаг; последние сообщения остаются в полном виде.
- Память ветки наследуется новой веткой, если точка ответвления не старше сохранённого резюме. Отдельная постоянная память проекта редактируется пользователем и добавляется в контекст каждой задачи проекта.
- Результаты вызовов инструментов сохраняются в истории. Одинаковые повторные вызовы блокируются; после ошибки доступа к файлу Workbench прекращает повторные попытки и просит модель выдать промежуточный результат.
- Лимит инструментальных шагов по умолчанию — 16 (настраивается в диапазоне 4–24); это ограничивает один запрос, а не всю задачу.
- Сообщение пользователя появляется в чате сразу после нажатия «Отправить», пока модель работает.
- Инструменты просмотра/чтения файлов, разрешённые проверки, поиск/чтение знаний через MCP. Проектный root определяется по проекту ветки, а не по одному глобальному PROJECT_ROOT.
- Универсальный защищённый ввод: `request_user_input` для обычных параметров и `request_user_secret` для паролей, PIN, OTP, passphrase и токенов. Секрет не добавляется в историю модели или SQLite открытым текстом.
- SSH-профили серверов с ключевой авторизацией через системный OpenSSH/ssh-agent и парольной авторизацией через Paramiko. Пароли хранятся в CredentialBroker: временно в памяти либо постоянно в Windows DPAPI CurrentUser.
- SSH-инструменты `ssh_read_file`, `ssh_run_command` и `ssh_run_profile_command`. Удалённая команда всегда ожидает отдельного подтверждения в панели; неизвестные host keys отклоняются.
- Git status и diff для контроля незакоммиченных изменений (только чтение).
- Запись файлов защищена: модель только создаёт запрос на изменение; пользователь подтверждает его в интерфейсе.
- Ручное создание контрольной точки ветки и экспорт Markdown-пакета переноса в другой чат. Полная история остаётся в SQLite.
- Загрузка файлов в чат кнопкой или перетаскиванием. Можно хранить вложение в текущей ветке, задаче или во всём проекте.
- Постоянное хранение вложений в `.workbench/uploads`; список, скачивание и удаление — в панели справа. В сообщениях сохраняются ссылки на отправленные файлы.
- Индексация текстовых и кодовых файлов, ZIP, PDF и DOCX. ZIP анализируется без распаковки на диск; для больших вложений модель умеет искать точные фрагменты отдельным инструментом.
- Импорт Markdown/TXT-пакета контекста в текущую ветку, новую ветку или новую задачу. Импорт попадает в память и не удаляет историю сообщений.

## Обновление существующей установки

1. Останови Workbench.
2. На всякий случай сделай резервную копию `.env` и всей папки `.workbench`.
3. Распакуй обновляющий ZIP поверх существующей папки `F:\SERGDATA-Workbench-Next`, соглашаясь на замену файлов приложения.
4. Запусти `start.cmd`. Скрипт установит новые зависимости из `requirements.txt` и запустит Workbench.

В обновляющем ZIP нет `.env`, `.workbench` и `.venv`: действующая SQLite-база, сохранённые вложения и локальные настройки остаются на месте.

## Зависимости и диагностика окружения

Основные Python-библиотеки приложения перечислены в `requirements.txt`. Они устанавливаются в отдельное виртуальное окружение `.venv` и не затрагивают системный Python. Для обычного запуска не требуется устанавливать pytest, Ruff или Node.js.

Дополнительные инструменты для разработки и проверок находятся отдельно в `requirements-dev.txt`: pytest (тесты Workbench), Ruff (проверка Python-кода), BeautifulSoup и html5lib (дополнительный разбор HTML). Установить их можно после основной установки: Windows — `install-dev.ps1`, Ubuntu — `./install-dev.sh`.

Для диагностики доступных компонентов запусти `python -m workbench.doctor` внутри виртуального окружения. Команда показывает версию Python, обязательные и дополнительные пакеты, а также наличие Git, Node.js, SSH и оболочек. Она ничего не устанавливает и не меняет. Отсутствие необязательного инструмента не считается ошибкой установки.

Git, Node.js/npm, OpenSSH и PowerShell — внешние системные программы, а не Python-пакеты; их нельзя добавлять в `requirements.txt`. Node.js нужен только для JavaScript-проверок, Git — для Git-функций, OpenSSH — для SSH-профилей с ключевой авторизацией. Парольная SSH-авторизация использует Python-библиотеку Paramiko из `requirements.txt`.

## Установка Windows PowerShell

1. Распакуй архив в `F:\SERGDATA-Workbench-Next` (или другую папку).
2. Установи Python 3.12+.
3. Выполни:

```powershell
cd F:\SERGDATA-Workbench-Next
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
Copy-Item .env.example .env
notepad .env
```

При первом запуске `start.ps1` создаст `.env` из `.env.example` и откроет его в Блокноте. Проверь пути `KB_SERVER`, `KB_CWD`, `KB_PYTHON`, `PROJECT_ROOT`. Существующий `.env` установщик не перезаписывает. Затем:

```powershell
python main.py
```

Открой `http://127.0.0.1:8787` в браузере. LM Studio должна быть запущена, модель загружена, Local Server включён.

## Установка Ubuntu / Linux

Требуется Python 3.12 или новее. На Ubuntu при необходимости установи базовые компоненты средствами системы (пример для Ubuntu/Debian):

```bash
sudo apt update
sudo apt install -y python3 python3-venv python3-pip
```

Распакуй проект, перейди в его каталог и запусти установщик: он создаст `.venv`, установит только основные Python-зависимости, выполнит диагностику, при необходимости создаст `.env` из шаблона и запустит Workbench. Проверь созданный `.env` и укажи реальные пути к Knowledge MCP и проекту. Существующий `.env` не изменяется.

```bash
chmod +x start.sh install-dev.sh
./start.sh
```

Дополнительные инструменты для разработки устанавливаются отдельно командой `./install-dev.sh`. Не запускай Workbench от root без отдельной необходимости.

**Важно о кроссплатформенности:** установка и диагностика совместимы с Windows и Ubuntu. SSH-профили доступны на обеих платформах при наличии Paramiko; ключевой режим дополнительно требует OpenSSH. Локальное выполнение произвольных команд по-прежнему использует PowerShell и не является универсальным Bash-исполнителем.

## История и база данных

Обновляющий архив не содержит SQLite-файлов. Приложение продолжает использовать существующую `.workbench/workbench.sqlite3`; миграции схемы выполняются добавлением таблиц/колонок и не заменяют пользовательскую базу.

## Управление контекстом

- Workbench получает активный размер контекста через LM Studio Python SDK только после проверки, что модель уже загружена. Это предотвращает случайную JIT-загрузку модели ради отображения статистики. Если SDK недоступен, применяется `loaded_context_length` из REST API, если поле доступно; иначе используется `CONTEXT_LIMIT` из `.env`. `max_context_length` модели показывается только как справочная максимальная ёмкость и не подменяет активный лимит.
- При превышении внутреннего порога Workbench просит модель сжать старые сообщения и сохраняет резюме в SQLite. Это отдельный запрос к модели и он тоже учитывается в usage, если LM Studio возвращает usage.
- При достижении 14 и более новых сообщений старые сообщения сворачиваются в память ветки; последние 8 остаются в полном виде. Внутри длинного цикла инструментов предусмотрено дополнительное сжатие истории запроса.
- Предварительный подсчёт модельным токенизатором точен для применённого prompt template сообщения; JSON-схема tools и служебная обвязка оцениваются отдельно. После отправки фактические `prompt_tokens` и `completion_tokens` из LM Studio являются источником истины.

## Вложения и импорт контекста

- При переносе задачи связанные с сообщениями вложения получают scoped-доступ в новой задаче через `task_attachment_access`. Файлы и исходные привязки не копируются/не изменяются; доступ не распространяется на другие задачи или проекты. Удаление исходного вложения отзывает все такие ссылки.


- Максимальный размер одного загружаемого файла — 20 МБ; за одно сообщение можно прикрепить до 12 файлов.
- ZIP: не более 300 файлов внутри и не более 80 МБ суммарного распакованного содержимого. Архив не распаковывается на диск. Индексируются текстовые/кодовые файлы; бинарные файлы сохраняются и доступны для скачивания.
- PDF индексируется по текстовому слою; сканированные страницы без текстового слоя автоматически не распознаются. DOCX извлекает абзацы и таблицы.
- `.env`, приватные ключи и сертификаты блокируются. Не загружай секреты в Workbench.
- Начальный контекст вложений ограничен 26 000 символами. Остальные фрагменты больших файлов модель может получать поиском `search_uploaded_files`.
- Импорт контекста ограничен 120 000 символами. При импорте в текущую или новую ветку уже существующая история сохраняется.
- Хранилище вложений находится внутри `.workbench`; при резервном копировании проекта сохраняй эту папку целиком. Она намеренно не включается в обновляющие архивы.

## Ограничения и честные оговорки

- API LM Studio может не возвращать usage для каждого локального backend/формата; тогда фактическая статистика останется нулевой, а оценка контекста будет отдельной.
- Если SDK `lmstudio` недоступен, предварительный подсчёт переключается на `tiktoken cl100k_base` и явно показывает этот режим. После отправки фактический usage берётся из LM Studio, если сервер его возвращает.
- Ответ модели с tool-calls не транслируется токен за токеном; интерфейс показывает ответ после завершения цикла инструментов.
- Проектные папки должны уже существовать на диске; приложение не создаёт их автоматически. Удаление проектов и перенос папок из UI пока не предусмотрены.\n- Память проекта пользовательская и редактируется вручную; автоматическое извлечение общих архитектурных фактов из всех задач пока не реализовано.\n- Git-интеграция показывает статус и diff, но не выполняет commit, checkout, reset или merge.\n- Создание ветки пока ответвляет диалог от последнего сообщения, не от выбранного сообщения.
- MCP подключается при старте приложения. Если сервер не найден, чат с LM Studio продолжает работать без MCP.
- Произвольные PowerShell-команды доступны только через очередь явного подтверждения пользователя. SSH-команды используют отдельный SSH Execution Engine и также требуют подтверждения. Типовые проверки запускаются через ограниченный список: pytest, ruff, compile, Git status и diff.
- Перед использованием на важных данных сделай Git commit/резервную копию.

## Безопасность

По умолчанию сервер слушает только `127.0.0.1`; код дополнительно запрещает bind на не-loopback адрес. Не публикуй этот интерфейс в интернет или локальную сеть без отдельной аутентифицированной архитектуры. Неизвестные SSH host keys не принимаются автоматически: сначала проверь fingerprint и добавь его в `~/.ssh/known_hosts`.


## Индикация заполнения контекста и API-учёт

- «Следующий контекст» — предварительная оценка следующего запроса после применения prompt template выбранной модели. Схема инструментов и служебная обвязка оцениваются отдельно; дополнительно отображается резерв под ответ.
- Размер активного контекстного окна берётся из LM Studio SDK (`get_context_length()`) только для уже загруженной модели. Если SDK не отвечает, применяется `loaded_context_length`, если он передан REST API, иначе резервный `CONTEXT_LIMIT`. Максимальный контекст модели (`max_context_length`) показывается отдельно и не считается активным лимитом.
- Каждый вызов LM Studio записывается отдельно: вход, выход, модель и тип операции (ответ, tool call, сжатие памяти). Последнее пользовательское обращение агрегирует все его внутренние вызовы, поэтому видно суммарный расход одного действия. Если сервер не вернул полный usage, вызов отмечается как неучтённый, а не как ноль; агрегат последнего обращения помечается неполным.
- Итог API показывает расход по видимой истории ветки. Расход родителя до точки ответвления показан отдельно от расхода самой ветки. Запросы родителя после точки ответвления в дочернюю ветку не попадают.
- Старые строки статистики из прежних версий сохраняются как исторические итоги. Детальная разбивка по отдельным вызовам начинает заполняться после установки этой версии.
- Workbench автоматически сжимает старую историю примерно при 62% рабочего лимита и дополнительно контролирует промежуточные циклы инструментов. Предупреждения интерфейса учитывают резерв под генерацию ответа.

Для модельного preflight-подсчёта устанавливается `lmstudio>=1.5.0` из `requirements.txt`. При недоступности SDK Workbench продолжает работать на резервной оценке `cl100k_base`, не выдавая её за точный токенизатор модели.

## Совместимость с шаблонами чата LM Studio

Workbench формирует одно начальное сообщение `system`: базовые правила, путь проекта, память проекта, задачи и ветки объединяются в нём. Это предотвращает HTTP 400 на шаблонах GGUF, которые не принимают несколько последовательных системных сообщений. Сохранённые результаты прошлых инструментов добавляются в хронологию как помеченные сообщения `user`; текущие вызовы функций остаются штатными OpenAI tool calls. Если LM Studio всё же отклонит запрос, интерфейс покажет доступную диагностическую часть ответа сервера.


## Надёжная работа агента с документами

- `search_uploaded_files` предназначен для поиска отдельных фрагментов и не подтверждает полноту документа.
- `read_uploaded_file` читает вложение по ID последовательными порциями. Продолжать нужно по `next_chunk`, пока результат не сообщит `ПОЛНОСТЬЮ ПРОЧИТАН`.
- Для анализа конкретного документа агент обязан сначала получить ID через `list_uploaded_files`, затем выполнить полное чтение. Для бинарных вложений без текстового слоя агент обязан сообщить ограничение.
- Повторная постановка одного и того же файла на подтверждение блокируется; конфликтующий вариант не создаётся автоматически.
- При разработке агент обязан следовать предварительным этапам и архитектурным ограничениям, зафиксированным в спецификации проекта.

## Локальное выполнение команд
В чате появилась панель «Локальное выполнение · PowerShell». Агент может подготовить команду через инструмент `execute_powershell`, но она не запускается автоматически. Проверь текст команды и нажми «Выполнить» только если понимаешь и разрешаешь её действие. Команда выполняется от имени текущего пользователя Windows, без повышения прав, из корня выбранного проекта; лимит времени — 180 секунд, вывод ограничен. Не подтверждай неизвестные команды, удаление данных, сетевые/системные изменения или команды с загрузкой и запуском неизвестного кода.

Типовые проверки (`pytest`, `ruff`, `compile`, Git status/diff) запускаются отдельным ограниченным инструментом. Для файловой навигации доступны список, чтение и поиск; секретные файлы и выход за корень проекта блокируются. Это локальный инструмент разработки, а не полноценная OS sandbox: подтверждение PowerShell-команды означает доверие к её содержимому.
