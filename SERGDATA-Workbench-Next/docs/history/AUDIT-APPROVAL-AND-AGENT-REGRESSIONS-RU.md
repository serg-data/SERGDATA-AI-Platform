Дата: 06.11.2026

## Что проверено

- Переходы состояния чата и кнопки Compute.
- Очередь ожидающих PowerShell/SSH-команд.
- Маршруты просмотра, одобрения и отклонения команд.
- Сохранение контекста исходного tool call и продолжение Agent.
- Адаптер текстовых вызовов инструментов для моделей, возвращающих `<tool_call>` в содержимом сообщения.
- SQLite-миграции и атомарность решений по pending-командам.

## Наблюдения по снимку базы из архива

- Execution #56: `completed`.
- Execution #57: `rejected` примерно через пять секунд после создания.
- Оба относятся к branch #30.
- Историческая карточка tool-call сохраняет первоначальный `pending` в metadata и не является текущим состоянием очереди.
- В прежней схеме не было полей, позволяющих установить, каким действием и когда пользователь одобрил/отклонил команду. Поэтому по старой записи нельзя доказать, кто нажал кнопку для #56 или #57.

## Исправления

1. Очередь выполнения обновляется в цикле опроса активности Agent, пока запрос обрабатывается. Новые pending PowerShell/SSH-команды отображаются без ручного обновления панели.
2. После получения данных очереди состояние кнопки Compute перерисовывается.
3. `/api/chat/status` сверяет временное состояние `waiting_approval`/`waiting_input` с постоянными очередями SQLite. После обработки последней команды старое состояние больше не должно бесконечно оставаться на кнопке.
4. Для будущих решений добавлены поля `approved_at`, `approved_via`, `rejected_at`, `rejected_via`.
5. Одобрение и отклонение выполняются атомарным условным UPDATE только из `pending`. Повторное действие не может повторно запустить или изменить уже обработанную команду.
6. Адаптер `extract_tool_calls` подключён к основному циклу Agent и циклу продолжения после завершения/отклонения команды. Неполные и неизвестные текстовые tool calls отклоняются, а не исполняются.
